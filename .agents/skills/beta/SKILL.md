# The beta channel and red changes

This skill holds what "Shipping a change" in AGENTS.md and the `ship` skill leave to a PR on beta and to a red change, numbered as AGENTS.md's list numbers its steps.

## The beta channel

- Each app has a beta channel: a second Worker, `<app>-app-beta`, from the `[env.beta]` in its `wrangler.toml`, with its own store, key, and address, whose page says beta on the Home Screen and in settings' version line (the root's `worker/build.mjs`). Its page also shows a tag beside the app's name, with the commit it runs and how long ago that went live (`writeRelease` in the root's `worker/page-files.mjs`, its age drawn by `shared/page/draw-channel-tag-age.js`). A push to the `beta` branch deploys it at once, with the same checks and rollback as `main`'s deploy, but only when the pushed commit is the head of the PR that holds beta (the root's `worker/beta-claim.mjs`). Each of `deploy:api`, `rollback`, `set-app-key`, `set-access-code`, `set-page-host`, `set-email-key`, and `set-rp-id` takes `--channel beta`.
- Beta holds one PR at a time, while the owner tests it on the phone. A PR claims beta with the `beta` label, and of the open PRs labeled `beta`, the one labeled first holds it. A PR waiting for beta has the `beta-wait` label, and the one labeled first has waited longest. On its watched same-repo PR events and each merge to `main`, the `Beta` workflow (`.github/workflows/beta.yml`) takes `beta` off a PR that closed, was pushed after its label, or got `phone-ok` after it, and off every PR but the one that holds beta, which it puts in line with `beta-wait`. Once beta is free, it comments on the PR that has waited longest, which wakes its session: "Beta is free, and this pull request has waited longest." A claim has no time limit, since the owner is the only tester. The deploy check reads labels live, so it sees a label change at once, even on a PR in conflict with `main`. GitHub starts no PR workflow for one in conflict, even after a push that leaves it in conflict. The workflow's label fixes and its comment wait for the next Beta run, which a merge to `main`, or a watched event on any same-repo PR not in conflict, this one included, starts.
- Change a PR's labels one at a time, never by setting its whole list, which would drop `phone-ok` or `review`: `gh pr edit <number> --add-label beta` or `--remove-label beta`, and the same for `beta-wait`. See who holds beta with `gh pr list --label beta --state open`, and who waits with `gh pr list --label beta-wait --state open`. Where a session has no `gh`, GitHub's issue tool sets a PR's whole label list, so read its labels just before and write them back with only the one change.
- To put a PR on beta:
  1. Push the branch once AGENTS.md's step 2 passes, without waiting for its CI or review, since beta's deploy runs its own checks, except in a red PR's round for `phone-ok`, as "Red changes" below says. A push gives beta up, so it comes before the claim. Merge `main` into it first only as AGENTS.md's step 3 says.
  2. Take `beta` off the PR if it still has it from before that push, since adding a label a PR already has changes nothing.
  3. Add `beta` to the PR.
  4. Confirm the PR holds beta: it does once it's the only open PR labeled `beta`. While another still has it, wait a minute for the `Beta` workflow and look again. If the workflow took `beta` off the PR, beta is held: see the next bullet.
  5. Take `beta-wait` off the PR if it has it, only now: taking it off first would tell the next in line, who would then lose the race.
  6. Push to beta: `git push -f origin <branch>:beta`.
  7. Wait for that push's Deploy run to say `worker check: ok` for each Worker, and tell the owner to use the beta app on the Home Screen. Name the commit the beta tag at the top of the app should show, so a build swapped since is plain to see.
- A design round tuned on the phone opens with an app's `page/tuning-round.json`, which names each CSS variable on `:root` to tune, with a slider's `min`, `max`, `step`, and `unit`, or a list of `options`, as `readRound` in `shared/page/tuning-round.js` checks. It tunes only a variable that's the same in every theme and at every width, since the panel reads each start once, as the page loads. Beta's build writes it into the page with the tuning panel, and production's leaves both out (the root's `worker/tuning-files.mjs`). The owner pastes back what the panel's Copy gives, and the PR sets those values in its stylesheets and deletes the round file in the same push.
- If beta is held, add `beta-wait` to the PR if the workflow hasn't, stay subscribed to the PR, and stop. The last message to the owner names the PR holding beta, with its link, and says the owner can say "put this on beta now" to take it. When the workflow's comment says beta is free, put the PR on beta from step 1.
- When the owner says "put this on beta now", take `beta` off the PR that holds it and add `beta-wait` to it, which puts it at the back of the line, then put this PR on beta from step 1. This is the only time a session changes another PR's labels, and only on the owner's word. If the workflow told another waiter before this PR took beta, it comments on that waiter that it stays first in line, or, when that waiter claimed beta meanwhile, takes `beta` off it. Either way, the workflow tells it again once beta is free.
- A PR gives beta up as it closes or merges, as its branch is pushed, and as the owner adds `phone-ok`, and the workflow takes the label off. Take `beta` off yourself when going back to work without a push yet, as when the owner's test found a problem, and when the owner is done testing a PR that isn't red, which never gets `phone-ok`. Take off both `beta` and `beta-wait` before saying the work is done.

## Red changes

- Take a red change to its branch and PR, put it on beta as soon as it's pushed, as "The beta channel" above says, and stop there: tell the user what to use on the phone, and wait, keeping to steps 4 to 6 of AGENTS.md's list meanwhile. Its PR stays a draft while the owner tries its design on beta: CI tests a draft, and beta deploys it, as for any PR, but Trusted review reviews it only once it's ready for review. Once the owner says the design is the one to keep, take `beta` off, since answering the review is going back to work, mark the PR ready for review, which starts its first full review, go on to step 7 and answer the review. Then, if `main` has a red commit the branch lacks, merge it, as the next bullet says. Once CI and Trusted review have passed on the head, put it on beta for the owner's `phone-ok`. When you ask the owner to add `phone-ok`, link the PR in the same message. Never add `phone-ok`. Only the owner labels it, once they've used the change on beta, which runs `gate` again without a push and gives beta up. A push after the label keeps it when nothing it changes since the head the owner labeled is red by the gate's rules, as with tests, docs, or tooling alone. A red change in that diff, like page code or a merge of `main` that brings in a red commit, holds the PR again until the owner has used that commit on beta and labeled it again, so put it on beta again and ask. So does a force push after the label, or a labeled head the gate can't find.
- One red change goes live per deploy. From a red PR's push to beta until it has merged and its deploy has finished, or it has closed unmerged, no other red PR merges. This window outlasts the beta claim, which ends at `phone-ok`. The gate holds an approved red PR when its tested head lacks any red commit on `main`, or when a red commit on `main` lacks verified production coverage. For a missing red commit, follow the re-approval steps above after merging `main`. The Red approvals workflow refreshes phone statuses after a merge to `main` and a completed main Deploy run. Those refreshes are asynchronous; a passing status is not an atomic merge lock. A production receipt records the target commit only after every repository Worker has fresh verification or runtime equivalent to earlier verified coverage. A skipped Worker without that proof creates no receipt. Receipts are retained for 90 days. The gate reads the last ten successful main Deploy runs and stays held when none has an unexpired receipt. A production deploy that verifies every Worker restores that evidence. When verification was unavailable, repair it and rerun the current eligible Deploy run, following `.claude/rules/tooling.md`, rather than bypassing the hold.

## Step 8: a red PR

- Merge a red PR only once `check` and `phone` passed with the `phone-ok` label on it: the label is the owner's sign-off from beta and their go-ahead to merge, so don't ask again, before the merge or once it's live. Until then, tell the user it's ready and wait. An OK in chat never stands in for the label. Merge it yourself: the owner doesn't.
- `check` holds the code that merges, the PR merged into `main` as `main` is then, so when `main` moved after the PR's last review, the run `phone-ok` starts fails `check` for want of a review. Answer it as the steward skill says for a `check` with no review on the code that merges.
