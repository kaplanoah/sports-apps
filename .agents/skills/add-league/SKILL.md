# Adding a league

A new league is a new app. Use `apps/wnba/` as a working example of app composition. Reuse the modules in `shared/` and implement only the league's own adapters and views. Keep the folder structure; adding a league needs no registry or new framework.

A league ships in parts. Its first PR holds what a fan opens the app for, by the steps below: the Worker and its store, the Games tab, the standings and bracket, each game's sheet with its box score, each team's sheet with its numbers, search, settings, the gate, the page's copy on the phone, both themes, and the beta channel. Each later PR adds one more part through the shared modules and the league's adapters, like rosters and players' sheets, a final's Highlights, a game's preview and lead chart, the News tab and its notifications, or the Updates box, with its tests and its places in search.

## Shared contracts and app responsibilities

- `createSeasonStore` in `shared/worker/season-store.js` owns persistence, alarms, retries, subscriptions, notifications, and background-job scheduling. Its `League<Snapshot, Updates>` contract carries the app's snapshot and notification-update types through the callbacks. The store reads only `snapshot.season`; game, standings, schedule, feed-failure, and update shapes remain the app's.
- Each app's `worker/src/store.js` declares its `League` type from its snapshot builder and `readUpdates`. The app's season updater decides what incomplete reads preserve, what changed, and which saved facts produce notifications. Reuse an existing shared helper when the behavior matches; never make shared code inspect an app name to choose league rules.
- `createAppWorker` owns routing and access. The app supplies its name, page files, and read endpoints. `listApps` discovers its `wrangler.toml`; build and test tooling use that discovery rather than a list of league names.
- Shared page modules own common interactions and views. Apps supply their data, fan vocabulary, render callbacks, and theme tokens. Keep feed identifiers, season selection, competition formats, scoring rules, and stat qualifications in the app. Similar field names alone do not establish the same behavior.
- Shared test suites own common assertions. Each app supplies recorded inputs and independent expected values. Keep league rules and approved design values in app tests; a shared helper receives them as inputs rather than branching on the app's name. Never read expected values from the production code being checked.

## Adding the app

While a league is being built, a sandbox Worker may try its feeds from Cloudflare, since a league can answer Cloudflare differently than it answers a cloud session. Name it `<app>-sandbox`, upload it from a scratch folder outside git with Cloudflare's API, as the root's `worker/deploy.mjs` does, and give it no page, store, key, or secret. Delete it once the app's first PR merges.

1. **Worker config.** `apps/<app>/worker/wrangler.toml` names the Worker `<app>-app`, binds the store, the gate's rate limit, and each service under `services/` by its name in capitals, and names the beta channel's Worker `<app>-app-beta` under `[env.beta]`, where it binds each service's `<name>-beta`, as the WNBA's does, which the root's `tests/deploy.test.js` checks for every app. The tooling finds apps by this file, and the root's `package.json`'s `#page-files/*` import, the lint, type, and dead code globs, and Playwright's projects all pick the new folder up from `apps/*`. Add `worker/page-files.mjs`, a one-line call to the root's `readPageFiles`.
2. **The league's data.** Put vendor requests and response parsing in `worker/src/adapters/`, as WNBA's `worker/src/adapters/wnba.js` and MLB's `worker/src/adapters/mlb.js` do. News feeds remain separate. Keep `page/js/snapshot.js` limited to the app-owned format, paths, and rules.

   `buildSnapshot(responses, { season, now })` in the adapter returns the season's games, series, standings, missing read details, and put-off starts. `choosePollDelay(snapshot, now)` supplies live state, starts, and live pace to `shared/page/poll-schedule.js`.

   Follow `.claude/rules/worker.md` for the sports-data boundary. Extend `shared/worker/sports-schema.js` and derive JSDoc types from its schemas. Malformed records must reach store status and feed health without replacing usable records or exposing raw payloads.

3. **Reading the feeds.** `worker/src/snapshot.js` coordinates adapters with `createSnapshotLoader()`, using `shared/worker/feed-keeper.js` for slower reads and saved answers. Preserve the league's explicit request budget, timeout, and refresh policy. Use `shared/worker/upstream.js`'s `createReusedLoader` for concurrent store-owned reads. Pages request only app records from their store.

   Build shared facilities in `shared/worker/` once, with both apps supplying league policy; never put a second identity table or vendor merge in an app. Check `.claude/rules/shared-modules.md` for the facilities available before extending them. A missing shared facility must be introduced there with its contract tests, rather than represented as an interface that already exists.

   Shared `identity.js` provides atomic scoped vendor lookup, discovery and reconciliation. `identity-matching.js` requires confident matching evidence, with explicit game numbers and corroborating teams and day for doubleheaders. Existing apps use `identity-documents.js` to register legacy internal IDs and backfill explicit facts without renaming records. Each identity policy names its `gameFactFields` so shared writes preserve those facts during ledger failures. Check health coverage before depending on a completed backfill. Reuse `identity-backfill.js` for nested checkpoints and persisted optional-work pacing; a document count alone does not bound its identities or storage reads. Change `IDENTITY_AUDIT_VERSION` when identity-writing or audit requirements change, not for unrelated releases. The optional-work allowance in `identity-backfill.js` does not cap total account usage.

   A new league should create opaque game and player IDs during ingestion with the shared lookup, keep vendor IDs in scoped mappings, and persist explicit season, competition, round and game-number fields. Never copy the existing apps' legacy assumption that an internal ID equals a vendor ID. Test concurrent discovery, repeated ingestion, postponements, resumed games, trades, uncertain matches and decisive repairs against actual storage.

   Opaque-ID readers, the vendor merge and per-part provenance are later prerequisites for the existing apps, not facilities implemented here. Introduce missing shared facilities with contract tests before a new league depends on them. The merge must keep coherent game state, rank eligible fresh answers above saved ones, preserve corrections and expose uncertainty in health.

   Route every new league read through its store, including details, search, and reminders. Confirm reminder candidates from fresh start and state facts. Use the app's `createReadDetail` store callback for detail routes, with shared `detail-reads.js` for concurrency and persisted answers. Worker entry points only forward those reads to the store. A failed storage read must not trigger a vendor request outside it.

   Implement historical filling with a background job's `updateHistory` callback. It runs after live jobs and reminders with `HISTORY_REQUESTS_PER_RUN` from the remaining `ALARM_REQUEST_ALLOWANCE` in the shared `request-budget.js`. Persist partial progress and fill newest seasons first; unfilled historical sheets use the shared Not available yet response.

4. **Keeping the season.** `worker/src/season-updater.js` saves each snapshot into the store, leaving a field as it was when a feed it needs didn't answer, and lists the notifications for what's new. `worker/src/store.js` hands those functions to the shared store with `createSeasonStore(league)`. `worker/src/index.js` builds the Worker with `createAppWorker`, naming its own league in `name`, and exports the store's class. A service's secrets, like the email service's, stay on the service, set once per channel, never copied into the league's Worker.
5. **The page.** `index.html` keeps the shared tab bar and settings markup, its element IDs, and the import map for `#shared/`. Its Games view is one empty `#seasonGames`, which `startDayStrip()` wires and `fillDayStrip()` fills with the league's game days. It loads the same shared stylesheets and scripts as the WNBA's, in the same order, around its own `styles.css`, which sets every token their top comments list. It calls `openLastTab()`, `showLastDrawn()`, `followSeasonPart()`, `watchSlowLoad()`, and `drawHomeScreenAsks()` right after its views and sheets, in that order, so a part on the shown tab can take back its sideways scroll, the header rides as far as the season's part put back, and the welcome opens over any sheet put back. Its `gate.html`, which asks for the access code, and its `sw.js`, which sets `self.pageName`, load the same shared files as the WNBA's too, which the root's `tests/apps.test.js` checks. It marks each element its code draws whole, like `#bracketWrap` and `#stamp`, with `data-last-drawn`, and keeps the empty `#loadNote` above its views.

   Give it a manifest, icons, and an `apple-mobile-web-app-title` of the league's short name, which its manifest's `name` and `short_name` match. Agree on the league's look with the owner from a mockup first: its fonts and its light and dark themes. The mockup is one plain HTML page that works on a phone, never a design canvas, with the WNBA's styles, separators, and layout from its `page/styles.css`, and only the new league's fonts and colors in place of its own. Once the views are built, look at each beside the mockup, with the same data, in each theme, and fix anything off.

   The league's fonts are self-hosted in `page/fonts/`, with each type role's size and weight, and the `--word-lift` that centers a row's words in its font, set in its `:root`, as `.claude/rules/page-look.md` says. The league's light and dark themes are each a set of colors, the dark one under `:root[data-theme="dark"]`, with icons of its own, which `page/js/looks.js` hands the shared `appearance.js` for the page and, through `page/js/gate-theme.js`, for the gate. The browser's bars take the theme's `--bg` floor, which the shared `pick-theme.js` reads from the stylesheet, linked before it. Choose the league's All-Star colors with the owner too: each All-Star team's star takes its uniform's color, as the WNBA's orange West and white East do, its visitors orange and its home team white in a year of captains' teams, and MLB's American and National League colors do, through `renderAllStarMark` in `shared/page/all-star.js`. The page's `styles.css` sets the star's tokens that `game-row.css` lists from the league's own dot. `page/js/league-words.js` names what the league's fans call things and the words its pages never show, as `.claude/rules/page-look.md` says, and its search terms hand it to the shared search as `words`.

6. **Tests.** The root's `tests/sports-boundary.test.js` discovers every app's pages and uses `listReachedFiles` from the root's `worker/browser-scope.mjs`. Extend its independent vendor policy when adding a vendor; prove indirect imports fail the guard. Record malformed responses alongside valid fixtures, verify validation under a runtime that forbids code generation, and assert unusable output preserves stored records and reports health failures.

   Exercise the actual live and historical writers with recorded full responses, empty seasons, malformed cold reads, failed updates over usable documents, and valid recovery.

   Count requests, including repeated, concurrent, failed, and timed-out reads, so historical work cannot starve live updates or reminders. Identity contract tests cover concurrent mapping and reconciliation. A missing merge facility needs its own tests for provenance, corrections and old links. The merge tests are acceptance criteria for that later work. Operational migrations and restore rehearsals need their separate authorization; automated stubs do not establish Cloudflare restoration or phone reload behavior.

   Record a real afternoon of the league's feeds as a fixture in `tests/fixtures/`, and test the snapshot, Worker, season updater, and page views against it. Adapt the WNBA app-specific tests for what the PR builds, keeping the league's own rules and recorded answers. The browser harness runs the page against the real store class in a simulated Durable Object context; it does not prove Cloudflare runtime behavior. `page.spec.mjs`, `themes.spec.mjs`, and `role-looks.spec.mjs` check type roles, contrast, periods, words, taps, and theme layout. The last two walk the app's `tests/browser/views.mjs`, which lists every tab and sheet the page has, since the shared theme suite fails on one no view opens. Its specs call each shared suite the root's `tests/browser/` exports, like `testThemes` and `testStreamedTabs`, which the root's `tests/shared-suites.test.js` checks. That test's `SUITES_NOT_YET_REACHED` names each suite whose part the app doesn't have yet, like the notification suites before News, and the PR adding the part calls the suite and takes it off. `at-rest.spec.mjs`, `settings-contact.spec.mjs`, and `word-centering.spec.mjs` also run in WebKit. Include `release-check.spec.mjs`, `access.spec.mjs`, and `offline.spec.mjs`.

   Call `testSeasonUpdater` from the root's `tests/season-updater-contract.js`, supplying the app's snapshot, updater, season key, and representations of unavailable and changed standings. It checks repeated and timestamp-only updates, preservation across failed reads, and recovery without redundant writes. The root's `tests/shared-suites.test.js` requires every app to call it. Keep app-specific final-state, concurrency, schedule, and feed-fallback cases beside it.

   Its `tests/search.test.js` names each place in `COVERAGE`, as `.claude/rules/page-code.md` says. Its `tests/search-typing.test.js` types every team, place, and player with the root's `tests/search-sweep.js`, from a recorded player list. The PR adding News and notifications includes `notification-layout.spec.mjs` and `notification-permission.spec.mjs`, which also run in WebKit. Each sheet joins `sheet-stack.spec.mjs` and `sheet-reload.spec.mjs` in the PR that adds it. Hand the deploy each channel's page secrets in `.github/workflows/deploy.yml`, and `Watch apps` production's in `.github/workflows/watch.yml`, which the root's `tests/deploy.test.js` checks.

7. **Docs.** Add the app to the README's table and its setup section's list of apps, and give it a `.claude/rules/<app>.md` of its own, as `mlb.md` and `wnba.md` are, and name it beside them in AGENTS.md's list of rule files.
8. **Ship it.** Open it as a `feat:` PR, which starts the app at version 1.0.0. Its page adds lines that give parts layers of their own, so it's a red change, tried on the owner's phone from beta before it merges, as the `beta` skill says. Each channel's token can edit only the Workers it names, so before the first deploy of each channel, the owner creates its Worker in Cloudflare's dashboard, as the README's "Deploying on merge" says, and adds it to that environment's token: `<app>-app-beta` to the `beta` token before the first push to `beta`, and `<app>-app` to the `production` token before the merge.

   Put it on beta as the `beta` skill's "The beta channel" says, whose deploy replaces `<app>-app-beta`. Hold later pushes as `.claude/rules/tooling.md` says, since a push leaves the Deploy run you re-run with nothing to check. Its first upload stays live but fails verification until its key, code, and page URL are configured. It answers nothing but `robots.txt` and `health` until `npm run set-app-key -- <app> --channel beta` gives it a key and prints its address. Give the owner that address, and ask them for its code, the one every app asks for, then run `npm run set-access-code -- <app> <code> --channel beta` yourself, which the owner approves when `.claude/settings.json` asks. Ask the owner to add the address as `<APP>_BETA_PAGE_URL` in the `beta` environment's secrets, beside its `ACCESS_CODE`. Re-run that Deploy run's jobs after the secrets are saved, following `.claude/rules/tooling.md`'s rerun requirements. Wait for this app's `worker check: ok` before asking the owner to add the page to the Home Screen and try it. Then go on as the `beta` skill's "Red changes" says, through its review to the owner's `phone-ok`.

   The merge's deploy then replaces `<app>-app`, which `npm run set-app-key -- <app>` gives its key in the same way. Its initial production upload also stays live but fails verification until its settings are saved. Ask the owner for production's existing code, the one every production app already asks for (the `production` environment's `ACCESS_CODE`), then run `npm run set-access-code -- <app> <code>` yourself, which the owner approves when `.claude/settings.json` asks. The owner adds its address as `<APP>_PAGE_URL`, beside the `production` environment's `ACCESS_CODE`, so each deploy and the `Watch apps` workflow open its page. After saving production's secrets, verify it by rerunning the current eligible Deploy run, following `.claude/rules/tooling.md`'s rerun requirements and superseded-run guidance, so the checked production receipt is restored. `Watch apps` supplies later health checks. A successful upload alone is not verification.
