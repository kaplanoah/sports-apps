# Trusted review's failures

This skill holds what step 7 of "Shipping a change" in AGENTS.md and the `ship` skill leave to a failed Trusted review job or CI's `review-join`.

- When the optional protected publisher is enabled, inspect `review-begin` when it fails and skips `review-plan`. Repair its publishing failure by `TRUSTED_REVIEW_SETUP.md`, then rerun the failed job; its dependent review stages start Claude. If `review-publish` fails while `review` passed, repair and rerun that publisher; it starts no Claude. Inspect lifecycle publisher failures separately. Never bypass the protected environment or required check.
- If Trusted review's `review` fails, read its summary and the log of the failed job, an area's `find` under `review-area`, or `review-across` or `review-post`. An area's `find` and `review-across` show the action's own errors but not each try's turns and tool calls, since they'd be public, and `review-post` shows the errors of the root's `worker/post-review.mjs`. If an area's `find` or `review-across` stopped before Claude started, like an install that timed out, re-run the failed jobs once yourself. Otherwise don't reproduce it locally or re-run it: each reviewer already tried twice, and the check across areas once. If `review-post` failed, re-run the failed jobs once yourself, since it starts no Claude and posts each finding only once. Tell the user what the log shows: an invalid or expired Claude credential secret, Claude unreachable, an error from `worker/post-review.mjs`, like a GitHub API call that failed, or a re-run that failed too. Once Trusted review's re-run passes, recover CI's join as below before `check` can pass.
- Provider-state failures show in `review-select`; credential and Codex activation-gate failures show in `review-plan`. Follow `TRUSTED_REVIEW_SETUP.md` to repair them. Only the owner may switch a gated PR to Claude with `review-provider:claude`; an agent never switches on its own.
- For Codex execution, inspect `review-codex` and `review-codex-across`, each with `request`, `model` and `validate` jobs. Retry a failure before model execution once after repairing its cause. Once a model started, report its failure without rerunning it unless the owner authorizes another attempt. Retry `validate` infrastructure once after repair, within the answer artifact's one-day retention; it starts no model. Expired answers require owner authorization for another model attempt. The answer artifact contains only the structured answer and available native usage counters; raw diagnostics stay on the disposable runner. A model failure's cause is not retained: report its failed step without guessing, and ask the owner to check the OpenAI credential and project usage.
- CI's `review-join` waits for and verifies Trusted review's result; it runs no Claude. If it fails, read its log for an API error, a timeout, missing evidence, or a result for different code or source. After Trusted review recovers by the preceding rule, re-run CI's join with `gh run rerun --job <review-join-job-id>`. This re-runs its downstream `check` too, even when the join succeeded with `owed=true` after a failed Trusted review. Re-running only failed jobs would reuse that successful join's owed result. Re-running the join starts no Claude; don't request another review merely to join a recovered result. If the PR's head or base changed, follow the steward skill to request review of the current code instead.
