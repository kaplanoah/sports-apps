# The Workers

- Sports feed parsing belongs in Worker adapters. The shared `espn-adapter.js` owns ESPN reads and parsing for both apps; apps supply league mappings and rules. The shared `sports-schema.js` configures Zod 4 with `jitless: true` and validates adapter output before persistence. Never import adapters or Zod from pages.
- The root's `tests/sports-boundary.test.js` checks every page import with `listReachedFiles`. Recorded adapter fixtures, malformed inputs, request counts, and store failure tests guard the boundary.

- Worker: `worker/src/`. It serves the page, its store, and its sheets' reads, only under `/<APP_KEY>/`; everything but `robots.txt` and `health` is a 404 without the key, but at the address its `PAGE_HOST` secret names, where it serves them without the key, behind the access code alone, and so only while it has one (`findAppPrefix` in `shared/worker/app-worker.js`). `health` says whether the Worker and its store answer, 200 or 503 with the release's commit, so an uptime monitor can watch it without holding a secret, and asks the store once a minute at most however often it's hit (`shared/worker/health.js`). It also says, under `services`, whether each service it binds answers and at which release, asked as seldom, apart from its own status, so an app whose service is down still answers 200. Under `feeds`, it says which of the league's feeds have failed every read for `FEED_FAILURE_MS` or longer, since when, and why, naming a URL by its path alone, which the store keeps in `live/feeds` from each update (`shared/worker/feed-failures.js`); a feed's failure alone never makes it a 503. An alarm in its Durable Object (`shared/worker/season-store.js`) keeps the current season's saved data up to date from the league, less often while no page has its socket open, and a page that opens brings the next update forward; the page only reads it. The alarm also wakes for reminder deadlines, fresh verification reads, and retries. The store tells a page as its socket opens whether that update is coming, and tells every page when each update is done, even one that changed nothing.

  When the Worker has an `ACCESS_CODE` secret, the page's address shows the app's `page/gate.html`, built from the shared `gate.js` and `gate.css`, and the season's data answers 401 until the phone sends that code. The Worker keeps the phone signed in with a cookie that holds a signature over the code, made with the `ACCESS_SIGNING_KEY` secret, never the code itself or the page's key, which every link shows (`shared/worker/access-gate.js`). A 401 reloads the page (`shared/page/access.js`). `count` takes only a POST, behind the access code and `ACCESS_LIMIT`, and writes the daily count to the `DAILY_OPENS` binding, which only production has, as the app's name and the request's hostname, so the counts tell the key's address from `PAGE_HOST`'s (`shared/worker/daily-count.js`).

  The Home Screen app's link to add the site again, whose browser keeps its cookies apart from the app's, signs the browser in with a handoff the Worker makes for a phone signed in, and opens the page at its own address without the handoff (`serveHandoff` in `shared/worker/access-gate.js`). A handoff is good for ten minutes under the code it was made under. The app asks for a handoff as settings shows the note on updating the icon, and again halfway through while it does, or as it comes back once that's past, since a phone freezes its timers while it's away (`shared/page/appearance.js`). The Worker moves its page from under the key to the `PAGE_HOST` address while it has both that secret and a code. It marks the page under the key as moving before the page reads its head. Under the key, a phone signed in gets a handoff at `PAGE_HOST` from `access/move` (`serveMoveHandoff`), and the page's address answers a phone that never signed in with a 301 to the same page there, which no browser keeps.

  Each update's news goes out as Web Push notifications (`worker/src/notifications.js`, `shared/worker/push.js` and `web-push.js`, and `page/sw.js`); the Durable Object makes and keeps the signing key itself, under a key the store's paths can't name. Playoff game reminders also go out as Web Push (`shared/worker/game-reminders.js`), and a tap opens the game (`shared/page/notification-intent.js`). The same service worker, which every load registers (`shared/page/service-worker.js`), keeps a copy of the page and every file it loads, and the pictures from other sites, like the News photos, that the page last showed (`shared/page/offline-worker.js`). So the page opens from the phone at once, even offline, while a newer page downloads behind it and replaces the copy only once all its files have arrived, and a page a deploy replaced reloads only once it has (`refreshPageCopy`). A copy the phone can't read leaves each request to the Worker, as if there were none, so a phone whose storage fails still opens the page whenever the Worker can answer. The service worker keeps its last steps, each start, install, activation, and push, and each page it opened and how, in a cache of its own, for Diagnostics to show (`shared/page/service-worker-steps.js`, read by `service-worker.js`). A phone the Worker signs out drops the copy (`shared/page/access.js`). Browser tests block service workers, whose requests skip the tests' routes, unless a test is about one.

  Deploys bundle it with all of the app's `page/` but a tuning round's `page/tuning-round.json`, which a channel off production writes into the page instead (the root's `worker/tuning-files.mjs`); `npm run build` writes each app's bundle to its `worker/dist/`, which git ignores. The build points the page's stylesheets, scripts, and import map into a folder named for its commit (`pinPageFiles` in the root's `worker/page-files.mjs`), which only that release's Worker serves, and browsers keep for good, so a page loaded mid-deploy never runs two releases' files together; when one is missing, `shared/page/release-guard.js`, written into the page's head, reloads it. The build also writes the release into the page, with beta's tag beside the app's name, so the page shows them as it opens, without asking the Worker (`writeRelease`).

- Read ahead of the page. What a view or sheet shows, the store reads in the background and keeps. Read only what may have changed with `createFeedKeeper`: game-dependent feeds as a game ends, other feeds once they are old. Prefer a whole-league request to one per player or team. Trim answers to the columns pages use and save only changed documents.
- Pages, detail routes, search, notifications, and reminders read only their store. The store owns vendor requests through adapters, including live reads triggered by a tap. Concurrent requests share `createReusedLoader`. Timed out or failed reads retain usable stored answers; when none exists, pages use shared Try again.
- Fill past seasons a little at a time, newest first. WNBA player/roster and MLB highlight `updateHistory` jobs run after live jobs and reminders, using `HISTORY_REQUESTS_PER_RUN` from the remaining `ALARM_REQUEST_ALLOWANCE` in the shared `request-budget.js`. Completed seasons are skipped until their reader version or schedule revision changes. Unfilled historical sheets use the shared Not available yet response.
- Retain game details in their canonical documents. Other detail answers use only the route's supported parameters, a bounded cache and an expiry (the shared `detail-reads.js`).

- The `accounts` service (`services/accounts/`): a Worker with no page or address, which each app reaches by its `ACCOUNTS` binding with RPC calls on its default export. Its one Durable Object keeps each account under a random id, with only its passkeys, keyed hashes of its emails, and each app's choices. It never keeps a name or an email as typed: an email is an HMAC under the service's own `EMAIL_KEY` secret (`worker/src/email-hash.js`). A choice saved keeps its write time, and the latest write wins (`worker/src/choices.js`). Its calls start and finish a passkey's registration and sign-in, read and save choices, remove a passkey, and delete the account, and they check passkeys with `@simplewebauthn/server` (`worker/src/accounts.js`). Every app's passkeys belong to the one site the service's `RP_ID` secret names, so a passkey made on one app signs in on the others, and its finishing calls take the origin of the caller's page, which the service trusts since only the apps' bindings reach it. Its health says it isn't ok while it lacks `EMAIL_KEY` or `RP_ID`, naming the secret and never a value (`worker/src/health.js`). The logic takes the store's storage, so a Node test runs each call against a fake authenticator (`tests/fake-authenticator.js`).

- The `email` service (`services/email/`): a Worker with no page or address, which each app reaches by its `EMAIL` binding to send its Contact reports. It holds the sender, recipient, and Resend key in its `CONTACT_FROM`, `CONTACT_TO`, and `CONTACT_MAIL_KEY` secrets, once per channel. Its `EmailOutbox` Durable Object stores each report, retries with Resend's idempotency key, and checks delivery (`worker/src/outbox.js`). IDs, rate limits, and queue caps are kept by league. Its health says it isn't ok while it lacks a secret or its outbox doesn't answer, and asks for attention while a report has waited over an hour or is paused, never naming a value or a report (`worker/src/service.js`).
