# Tooling

- CI runs every Node test once in UTC, then repeats the explicit `tests/time-zone-sensitive.json` sensitive list and changed Node tests in Honolulu (`worker/test-time-zone.mjs`). `worker/time-zone-scope.mjs` verifies native Date/Intl coverage with `listReachedFiles` in `worker/browser-scope.mjs`. Missing coverage or unreadable changes fail instead of silently narrowing the run. The manifest's `browserOnly` adapters run only in browser tests. A native time API source without a Node import path needs a test before CI can pass. Tests in the manifest's `fixed` list import `tests/eastern-time-zone.js` first, so their initialization and assertions use Eastern whatever zone they inherit. They are left out of the Honolulu run.
- Tooling: the root `worker/` builds, versions, deploys, and rolls back every Worker, each app's and each service's, tells a red change for CI's gate, and keeps beta to one pull request at a time, as the `ship` skill's "The beta channel" says. `ls worker/` lists its modules, and its tests are in the root `tests/`. It opens each app's live page as a phone does, signed in with its code, and says whether it drew what its store sent (`check-page.mjs`). It checks the page where a browser lands, which for an app moving to its own address is that address.

  The Red approvals workflow (`worker/red-approval.mjs`) refreshes phone statuses when main or its deploy changes, checking all missing red commits and verified production coverage. The deploy supplies that evidence through the checked production receipts described in the ship skill's "Red changes" section.

  A deploy restores earlier versions when route setup fails or checks find a broken Worker, page, or service, including one answering at the wrong release. Missing page or access-code settings, refused or rate-limited codes, a page that opens without asking for its code, and unavailable browser checks fail verification while leaving the uploaded version live but unverified. An explicit GitHub rerun (`GITHUB_RUN_ATTEMPT > 1`) checks an unchanged app at its recorded live commit, without uploading or rolling it back. That commit must be the requested commit, or in production a proven ancestor with equivalent runtime in the app's scope. Automatic follow-up runs and apps without that proof keep their normal skip. A rerun still needs the current channel head and beta claim; a superseded run checks nothing. Complete a new league's beta settings and verification before pushing another commit. After production's deploy has been superseded, inspect the newer Deploy run. If verification was unavailable, repair its configuration or access and rerun the current eligible Deploy run to verify all apps and restore the checked production receipt. `Watch apps` checks live health but cannot restore that receipt.

  While production's deploy fails, the Deploy workflow's `report` job keeps one open issue, "The production deploy is failing", which a run that checks the live apps closes (`report-deploy.mjs`). A run that checks nothing, like a superseded one, leaves it as it is, but a deploy cancelled after it started, as by its time limit, counts as failed. Only this job has `issues: write`, so the job holding the Cloudflare token can't write issues, and this job's failure never fails the run.

  The `Watch apps` workflow opens each page the same way every 15 minutes, keeping one open issue for each app that isn't opening, which closes once it opens again, and one for each that opens without asking for its code, which closes once it asks again (`watch-apps.mjs`). The deploy and the workflow both read each page's address from the `production` environment's secrets, as `<APP>_PAGE_URL`, and the one code every app asks for as `ACCESS_CODE`. A beta deploy reads them from the `beta` environment's, with `_BETA` after the app's name in each address's.

- Services: each deploy uploads every service before any app, since an app binds each service, by its name in capitals, to its Worker on the app's channel (`listServiceBindings` in the root's `worker/deploy.mjs`). After all app deploys settle, the deploy checks every service, including unchanged services an app can newly bind. A service has no workers.dev address, so the check reads what each app's `health` says of it, in a field of its own, `services.<name>`, apart from the app's own status, and puts the service's earlier version back unless every app that reports it says it's ok at the new commit (`worker/check-service.mjs`). An unchanged service is checked at its own live commit and isn't rolled back. A service with a known release is skipped only when no app's live version binds it. A manual `deploy:api` that names one app fails if a service has no recorded live commit, even when no app binds it yet; deploy all Workers to upload that service first. The service reads its release from its `VERSION` binding, which the upload's `workers/tag` sets to the short commit. The `Watch apps` workflow checks each service the same way, keeping one open issue for each that isn't answering, which closes once it answers again. Each channel's Cloudflare token edits only the Workers it names, so before a service's first deploy on a channel, the owner creates its Worker and adds it to that environment's token, as the `add-league` skill says for an app.
- The protected App publisher validates trusted-review evidence on main before writing the independent head check. `TRUSTED_REVIEW_PUBLISHER_ENABLED` stays unset until protected setup and live proofs pass. See `TRUSTED_REVIEW_SETUP.md` for setup and recovery.
- Hooks in `.claude/settings.json`, each saying why when it blocks a call, and all off in CI's review:
  - `.claude/hooks/one-command.mjs` blocks a call that starts with `cd` or joins commands.
  - `.claude/hooks/context-limit.mjs` hands a session off to a fresh one as its context grows. After its stop, commands run alone with literal arguments: no variables, glob or brace expansions, leading `~`, pipes, redirects, or command substitutions. Quote arguments containing `{`, `(`, or `)`, except the literal `{owner}/{repo}` placeholders. A heredoc with a quoted delimiter on stdin can supply a commit message or PR body.
  - `.claude/hooks/install-packages.mjs` sets `core.hooksPath` to `.githooks` at every session start, even with current packages, and runs `npm ci` when `node_modules` is out of date.
- `npm install` and `npm ci` install `.githooks/pre-push` through the root package's `prepare` script. Git runs `.claude/hooks/check-push.mjs` for every client. Commits already contained in local `origin` tracking branches need no repeat checks, regardless of the destination branch. Deletions need none. An unpublished commit must be `HEAD` with a clean tree and packages installed; otherwise check it out and push it separately.
- Claude's context-limit stop permits `git push --no-verify origin HEAD` only to save the session's own branch for handoff. Commit the work first, record any failed checks in the PR description, give the owner a complete continuation prompt, and stop. The next session fixes failures before normal shipping; this escape never permits bypassing CI or merging a failing PR. Codex has no equivalent context-limit or one-command enforcement.
- A hand deploy needs `<APP>_PAGE_URL` (`<APP>_BETA_PAGE_URL` for beta) and `ACCESS_CODE` in the session's environment to verify its app. `ACCESS_CODE` must match the channel being deployed, which may use a different code on beta. Allow both the Worker host and any custom page host in the session's network settings. Chromium also needs network access and trust for the environment's proxy certificate; `NODE_USE_ENV_PROXY=1` configures only Node's requests. Proxy failures leave the page unverified. An untrusted certificate does too with a proxy configured in the environment; without a proxy it counts as a broken page. Without the page settings, an upload stays live but fails verification. For standalone setup, follow the README's environment settings and manual page check. With GitHub deployment configured, re-run the Deploy run's jobs after saving its page secrets, following the rerun requirements above.
- A session runs `deploy:api`, `rollback`, and each `set-` script itself, in the cloud environment that holds the Cloudflare token, and the owner approves each when `.claude/settings.json` asks. Never hand the owner one to run on their own computer, which has neither the token nor the account ID, unless they ask to.
- `npm run rework` estimates follow-up fixes from overlapping files in merged PRs and reports their monthly share. Run `git fetch origin main` first, since it reads the locally fetched `origin/main` and a stale fetch gives a stale report. It fails if that reference is missing. File overlap is an estimate, not proof that an earlier PR caused a fix.
- `npm run rollback -- <worker>` puts an app's or a service's previous version back at all of its traffic and prints which commit was live and which is now. Run it only when the user asks.
- `npm run set-app-key -- <app>` gives that app's Worker its `APP_KEY` and prints the page's address. `--rotate` replaces the key, which changes the address; do that only when the user asks.
- `npm run set-access-code -- <app> <code>` sets the code an app's page asks for, with a new random `ACCESS_SIGNING_KEY`; the user picks the code. Every app on a channel takes the same code, since the deploy and the workflow sign each in with the environment's one `ACCESS_CODE`. A new code signs every phone out, and `--remove` stops asking, which makes later app deploys fail verification. Never commit, log, or post the code.
- `npm run set-page-host -- <app> <host>` points a host on a domain in the Cloudflare account at that app's Worker and names it in the Worker's `PAGE_HOST` secret, so the page also opens there without its key, behind its access code, which it needs first; the user picks the host. The address with the key keeps working, and phones stay signed in there. While the Worker has both the host and a code, it marks the page under the key as moving and sends fans on with their choices, a browser at once and a Home Screen app from a card in its Updates box (`shared/page/page-move.js`). Keep the host out of the repo, as the Worker's own address is.
- `npm run set-email-key` gives the accounts service the `EMAIL_KEY` secret it hashes each email under, made at random and never printed, with `-- --channel beta` for beta's. It refuses when the Worker already has one, since a new key would leave every account's email unfindable. Run it once on each channel, once the service's Worker exists and the channel's token can edit it, before the service's first deploy there, which keeps it.
- `npm run set-rp-id -- <domain>` names, in the accounts service's `RP_ID` secret, the site every app's passkeys belong to, with `--channel beta` for beta's. It's a domain each app's `PAGE_HOST` on that channel is under, since the service checks each passkey against the origin of the caller's page. It never prints the domain, and refuses when the Worker already has one, since a passkey signs in only to the site it was made under. The owner picks the domain; run it once on each channel, beside `set-email-key`; keep the domain out of the repo, as the page hosts are.
- Until the accounts service has both secrets, its health says it isn't ok, naming the secret missing, and registration and sign-in refuse.
- Mask, in anything a workflow logs or posts, what AGENTS.md's public-repo bullet keeps out of the repo, as `hideAddress` in the root's `worker/check-page.mjs` masks a check's reason.
- A Worker's deploy is skipped when nothing but docs, tests, tooling, and other Workers' folders changed since its live version's commit; the root's `worker/deploy-scope.mjs` lists those files. It skips the root's `.claude/`, `.agents/`, and `.githooks/` folders whole, so a new hook, rule, or skill needs no entry. When you add any other file that can't change the Worker, add it to that list. A service's `wrangler.toml` deploys that service and every app, since each app binds the service by it, so adding, renaming, or removing one deploys them, but no other service.
