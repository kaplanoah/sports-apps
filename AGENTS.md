# AGENTS.md

## Code

- Keep code clean, consistent, reliable, readable, secure, and maintainable.
- Follow best practices. Don't be unique or clever.
- Leave code better than you found it. Don't leave something sub-optimal just because that's how you found it.
- Start function names with a verb naming the action (boolean predicates excepted). No generic names like `call`, `run`, `execute`, or `handle`.
- Make every function do one thing well. Make orchestration a sequence of named steps. Extract and name any non-trivial logic inside blocks or chained conditions.
- Name variables with full words that are reasonable for their types. No opaque abbreviations.
- Default to no comments. Only use a comment for a non-obvious why. Every comment must be evergreen: no history narrative, no call-site lists, no fixture values, nothing that restates the code.
- Use plain ASCII in code, comments, docs, and commit messages: no em dashes, no curly quotes.

## Tests

- Every change to behavior comes with tests that fail without it, in the same PR. Before pushing, break the code each new test guards and watch it fail; a test that still passes guards nothing.
- Test text, numbers, and logic in Node, where a test takes milliseconds: render the view's markup or call the function, as `apps/mlb/tests/page.test.js` does for the Games list's series labels. Write a browser test only for what takes a browser: layout, color, motion, focus, and the page working with its Worker and store.
- In a browser test, wait for what the page shows, with `expect(locator)` or `expect.poll`, never for a fixed time or for the network to go quiet; lint rejects `waitForTimeout`, `setTimeout`, and `networkidle`. Get past the page's timers and animation frames by moving its fake clock with `page.clock.runFor`, and past a scroll by waiting for its `scroll` or `scrollend` event.
- A browser test that passes only some of the time has a bug to find and fix, in the page or the test, in its own PR. CI retries a failed browser test once, so it can't fail a pull request it has nothing to do with, and GitHub's reporter marks each one that passed only on its retry on the pull request's checks, the run keeps its failed try's trace, and the `check` job adds it to the table in the issue Flaky browser tests. CI's `burn-in` runs each browser spec a pull request adds or changes ten times with no retry, in WebKit too for the at-rest specs, and each night main's browser tests run three times over with no retry and add each test that failed to the table in the open issue Flaky browser tests (`.github/workflows/flaky.yml` and `worker/report-flaky-tests.mjs`), which comments on each test new to it, drops a test once it hasn't failed for a week, and closes once none is left. To reproduce a flaky test, or to show a fix holds, run that workflow by hand with the tests, the project, the branch, and how many times to run each: it runs on the machine CI uses, WebKit included, which a cloud session doesn't have. After a reload whose page code a test holds, the copy the page puts back has already taken the load note away, so the test waits for `domcontentloaded` to know the code has run.
- Route a browser test's requests by a pattern, like the root's `matchPath` in `tests/browser/harness.mjs`, never a function, which makes Playwright ask the test about every request the page makes and slows each load; lint rejects one. To unroute one of two routes with the same pattern, name its handler too.
- Before a test changes what the page reads next, wait until the page shows its last read, or the change races the read still on its way.
- A theme changes only colors, so each view lays out the same in each of an app's themes. The WNBA's `tests/browser/themes.spec.mjs` checks every view in Walnut against Maple, on a phone and a wide screen, with the root's `tests/browser/theme-layout.mjs`; a new view joins its list.
- Sheets look alike. Every sheet's top is a band, from `.sheet-page .sheet-top` in `shared/page/sheet.css`, never a list of sheets, as tall as what it holds: the WNBA's is the floor's color over the card's, ending in a line, with each title at the same height on every sheet and what goes with it, like a game's teams and score, in the band under it. Sheets, and a sheet's sections, slide side by side with the app's `--sheet-gap` of the sheet's color between them, each band's sides edged in its line while they move, so two bands never have to meet. `tests/browser/sheet-stack.spec.mjs` opens every sheet on the page and checks each top; a new sheet joins its list, or the test fails.
- A reload draws each open sheet as it was. A sheet that reads from the Worker keeps what it read in its `keeper` (`wireSheet` in `shared/page/sheet.js`), beside what it shows, and draws again from that while it reads again, never its placeholders, as the game sheet does with its box score and a team's sheet with its roster (`sectionsKeeper` in `shared/page/team-sheet.js`). The WNBA's `tests/browser/sheet-reload.spec.mjs` reloads each sheet with its reads held and checks it shows the same; a new sheet joins its list, or the test fails.
- A browser test that isn't about motion asks for reduced motion, with `page.emulateMedia({ reducedMotion: "reduce" })` or, for a whole file, `test.use({ contextOptions: { reducedMotion: "reduce" } })`, so it doesn't wait out eased scrolls and springs. Each animation keeps a full-motion test of its own. A gesture, like a swipe, is tested both ways too: its full-motion test drives it with the root's `tests/browser/touch.mjs`, as a finger does, and checks what moves and what doesn't once the finger lifts, since a motion that replays or jumps then shows only in full motion. A drag's moves come as a flick unless its `durationMs` spreads them out, so a test of a drag that comes to rest before the finger lifts gives one. A swipe is checked frame by frame: where what it moves is on each frame, never stepping back, and that the page changes nothing while the finger moves it but where that is, as the WNBA's `sheet-stack.spec.mjs` does for a sheet's swipe back.

## Adding a league

A new league is a new app. Copy the WNBA's: it's the newest, and every file below has a working example in `apps/wnba/`.

1. **Worker config.** `apps/<app>/worker/wrangler.toml` names the Worker and binds the store, as the WNBA's does. The tooling finds apps by this file, and `package.json`'s `#page-files/*` import, the lint, type, and dead code globs, and Playwright's projects all pick the new folder up from `apps/*`. Add `worker/page-files.mjs`, a one-line call to the root's `readPageFiles`.
2. **The league's data.** `page/js/snapshot.js` names the league's feeds and turns their answers into one snapshot: `buildSnapshot(responses, { season, now })`, with the season's games, series, and standings and a `missing` list of feeds that didn't answer, and `choosePollDelay(snapshot, now)`, which hands the shared one in `shared/page/poll-schedule.js` whether a game is live, the starts still to come, and the league's live pace. It runs in both the page and the Worker, so it uses no DOM and no globals.
3. **Reading the feeds.** `worker/src/snapshot.js` fetches them with `createSnapshotServer()`, reading each slow feed again only as a game ends or once it's old, and keeping its last good answer for when a read fails, with the shared `createFeedKeeper` in `shared/worker/feed-keeper.js`.
4. **Keeping the season.** `worker/src/season-updater.js` saves each snapshot into the store, leaving a field as it was when a feed it needs didn't answer, and lists the notifications for what's new. `worker/src/store.js` hands those functions to the shared store with `createSeasonStore(league)`. `worker/src/index.js` builds the Worker with `createAppWorker` and exports the store's class.
5. **The page.** `index.html` keeps the shared tab bar and settings markup, its element IDs, and the import map for `#shared/`. Its Games view is one empty `#seasonGames`, which `startDayStrip()` wires and `fillDayStrip()` fills with the league's game days. It links `shared/type.css`, `shared/chrome.css`, `shared/game-row.css`, `shared/pager.css`, and `shared/day-strip.css` before its own `styles.css`, which sets every token their top comments list, loads `shared/release-guard.js` first in its head and `shared/open-last-tab.js`, `shared/show-last-drawn.js`, and `shared/slow-load.js` after its stylesheets, marks each element its code draws whole, like `#bracketWrap` and `#stamp`, with `data-last-drawn`, keeps the empty `#loadNote` above its views, and calls `openLastTab()`, `showLastDrawn()`, and `watchSlowLoad()` right after its views and sheets, in that order, so a part on the shown tab can take back its sideways scroll. `gate.html` asks for the access code: copy the WNBA's, with the league's icon and colors, which `styles.css` hands `shared/gate.css`, linked after `shared/type.css`, through the tokens its top comment lists. `sw.js` sets `self.pageName` and imports `shared/push-worker.js` and `shared/offline-worker.js`. Give it a manifest, icons, and an `apple-mobile-web-app-title` of the league's short name. Choose the league's All-Star colors with the owner: each All-Star team's star takes its uniform's color, as the WNBA's orange West and white East do, its visitors orange and its home team white in a year of captains' teams, and MLB's American and National League colors do, through `renderAllStarMark` in `shared/page/all-star.js`, and `styles.css` sets the star's tokens that `game-row.css` lists from the league's own dot.
6. **Tests.** Record a real afternoon of the league's feeds as a fixture in `tests/fixtures/`, and test the snapshot, the Worker, the season updater, and the page's views against it. Browser tests in `tests/browser/` run the page against the real store, as the WNBA's harness does.
7. **Docs.** Add the app to the README's table and its setup section's list of apps, and to the "Apps" bullet above.
8. **Ship it.** Open it as a `feat:` PR. The app starts at version 1.0.0, and the merge's deploy creates its Worker, which answers nothing but `robots.txt` until `npm run set-app-key -- <app>` gives it a key and prints the page's address.

## Workflow

- `main` is the source of truth. Every change reaches it through a PR, by the steps in "Shipping a change" below.
- Never push to another session's branch.
- Don't spend time curating commit history. Squash merges make it irrelevant.
- Refer to PRs by number, not branch.
- Start every PR title with a type. The squash merge carries it to `main`, where it sets the next version of each app it changes (`worker/release.mjs`); a PR that changes nothing an app's deploy counts (`worker/deploy-scope.mjs`), such as only its tests or other apps' folders, leaves that app's version alone: `feat:` for something new to see or do (minor), `fix:` for fixes and polish (patch), `refactor:` for code the Worker runs with no visible change (patch), `build:` for dependencies, the build, and the deploy (patch), and `docs:`, `test:`, `ci:`, or `chore:` for changes the deploy skips (no version). Add `!` after a type that releases, as in `feat!:`, for a major change: a new address, lost data, or something that's gone. It's major for every app the PR's deploy changes, through shared code too; when only one app breaks, name it, as in `feat(mlb)!:`, and the others take the type's own bump. A scope is only for that. A PR that mixes kinds takes the biggest bump. CI's `title` job checks it.
- Release notes: each app's `page/js/release-notes.js` lists what's new in the app, which its Updates box shows under New in the app for two weeks from each note's `at`, until it's dismissed. Add a note only when the user asks for one, whatever the PR's type, in the words they approve, with an `at` just before the PR merges. A word that should stand out, like a button's name, goes in `<b>`, in a note built with the `html` template, which the Updates box sets a step heavier than the note's text.
- Each app has a beta channel: a second Worker, `<app>-app-beta`, from the `[env.beta]` in its `wrangler.toml`, with its own store, key, and address, whose page says beta on the Home Screen and in settings' version line (`worker/build.mjs`). A push to the `beta` branch deploys it at once, with the same checks and rollback as `main`'s deploy. To use a PR's change on the owner's phone before it merges, reset `beta` to the PR's branch and push (`git push -f origin <branch>:beta`), wait for that push's Deploy run to say `worker check: ok` for each app, and tell the user to use the beta app on the Home Screen. `beta` is a scratch branch: never commit to it or open a PR from it. Each of `deploy:api`, `rollback`, `set-app-key`, and `set-access-code` takes `--channel beta`.
- A red change is one whose bugs no CI browser would show, since none touches, scrolls, layers, and draws as an iPhone does, or that touches what iOS has drawn wrong before: parts left undrawn by how layers and sheets stack. `worker/red-change.mjs` finds it: any change to the shared JavaScript that moves and draws the page (`sheet.js`, `sheet-reopen.js`, `slide-panels.js`, `sheet-swipe.js`, `sheet-sections.js`, `side-swipe.js`, `pager.js`, `pill-thumb.js`, `tab-bar.js`, `eased-redraw.js`, `show-last-drawn.js`, `day-strip.js`, and `strip-slide.js` in `shared/page/`); a change to its shared stylesheets (`sheet.css`, `pager.css`, `chrome.css`, `team-sheet.css`, `game-cards.css`, and `day-strip.css`), added or removed, in a selector or at-rule, which says which parts a rule reaches, or in a property that decides how parts layer, stack, scroll, take a touch, or show (any below, any `position`, `overflow`, `overscroll-behavior`, `scroll-snap`, `touch-action`, `z-index`, `opacity`, `visibility`, `display`, `isolation`, or `mix-blend-mode`), but not in their fonts, colors, spacing, or sizes, which CI checks; or an added line in a page's CSS or JavaScript that sets a property that gives a part a layer of its own (`transform`, `filter`, `backdrop-filter`, `mask`, `clip-path`, `will-change`, `animation`, `transition`, `contain`, `content-visibility`, or a fixed or sticky `position`). Tests are never red. The owner's phone is a red change's test, and CI's `gate` job fails on one until its PR has the `phone-ok` label.
  - Take a red change to its branch and PR, deploy it to beta as the bullet above says, and stop there: tell the user what to use on the phone, and wait, doing only what CI and the review ask of the PR meanwhile. Never add `phone-ok`. Only the owner labels it, once they've used the change on beta, which runs `gate` again without a push. Merge a red PR once `check` passes with `phone-ok` on it: the label is the owner's sign-off from beta and their go-ahead to merge, so don't ask again. An OK in chat never stands in for the label. Merge it yourself: the owner doesn't.
  - One red change goes live per deploy. While a red change is on beta, or has merged and the owner hasn't confirmed it on the phone, no other red PR merges, and none replaces it on beta.
  - If parts of a page ever stop drawing on the phone again, the first step is a phone restart and a Diagnostics report from settings, not a code change.
- `npm run rollback -- <app>` puts the app's previous version back at all of its traffic and prints which commit was live and which is now. Run it only when the user asks.
- `npm run set-app-key -- <app>` gives that app's Worker its `APP_KEY` and prints the page's address. `--rotate` replaces the key, which changes the address; do that only when the user asks.
- `npm run set-access-code -- <app> <code>` sets the code an app's page asks for, with a new random `ACCESS_SIGNING_KEY`; the user picks the code. A new code signs every phone out, and `--remove` stops asking. Never commit, log, or post the code.
- The repo is public. Never commit secrets, keys, account IDs, real Worker addresses or subdomains, or personal data; use placeholders in tests and docs.
- The Cloudflare token lives only in the cloud environment's API credentials and the repo's `production` GitHub environment. Never ask for it in chat or put it in environment variables, code, or commits.
- Keep scratch work (design playgrounds, test harnesses) out of git, and never point tests at the real page.
- When unsure, do what best serves the intent of the work, and confirm with the user. If you genuinely need a decision from the user, give all the context concisely, list the pros and cons of each option, and make a recommendation.

### Shipping a change

Follow these steps in order. When a step says to go back to an earlier step, continue in order from there.

1. Fetch `main` and start your branch from it, or, for a stacked PR (step 12), from the branch of the PR it builds on. If the branch's last PR has merged, reset the branch to `origin/main` first.
2. Run `npm run lint`, `npm run format:check`, `npm run typecheck`, and `npm run deadcode`, and the tests that cover what you changed: a test file with `node --test <file>`, or a browser spec with `npx playwright test <file>`. Even for a change to shared code, run the specs that exercise it by name, found by searching the tests for the module or the elements it draws; never pass a folder. Don't run the full test suite locally (`npm test`, `npm run test:browser`, or `npm run check`): CI runs it on every push. If anything fails, fix it and run it again. Repeat until it passes. Never push while it fails.
   - Before pushing a change to how a page looks, screenshot every view it touches, in each of the app's themes, on a phone and a wide screen, and look at each one: a test checks only what it names. Look at a view built from a mockup beside the mockup, with the same data, and a new view beside its siblings, like a new sheet beside the others, rather than on its own. Fix anything off, and name the views and themes you looked at in the PR's description.
   - The browser tests run in CI on Chromium's headless shell, which behaves differently from full Chromium; for example, it denies notification permission. If you set `CHROMIUM_PATH`, point it at the headless shell. Set `BROWSER_TEST_PORT` to run a second checkout's browser tests alongside another's, on that port and the next.
3. Fetch `main` and merge it into your branch, or, for a stacked PR, the branch of the PR it builds on. If that brought in anything new, go back to step 2. Then commit, push, and open a PR into `main`, or a stacked PR into the branch it builds on. If the PR is already open, the push updates it.
   - If the change is red (`node worker/red-change.mjs` with the branch's diff from `main` on stdin says why), also deploy it to beta once its CI passes (`git push -f origin <branch>:beta`, as "Workflow" says), unless another red change is still on beta or unconfirmed. Then tell the user it's on beta and what to use on the phone, and keep to steps 4 to 7 while the owner tries it.
4. Check whether the PR has merge conflicts with its base branch. GitHub runs no CI on a PR with conflicts, so waiting on one would never end. A merge to `main` that leaves an open PR in conflict comments on it (`worker/flag-conflicts.mjs`), which wakes a session watching it. If it has them, merge the base branch into your branch, resolve the conflicts, and go back to step 2. If resolving a conflict would drop behavior from either side, resolve it in the way that best serves the spirit of both changes, and confirm with the user. If you genuinely need a decision from the user, give all the context concisely, list the pros and cons of each option, and make a recommendation.
5. Wait until every CI job on the PR's latest commit has finished. The `check` job is the one that must pass; it fails whenever any other CI job fails. Each time you look while waiting, and whenever no CI run has started on the latest commit a few minutes after the push, go back to step 4 first: another PR may have merged into `main` and left this one in conflict.
6. If a CI job failed, read its log and reproduce the failure locally. Fix it and go back to step 2. If you can't reproduce or fix it, tell the user which job failed, what its log says, what you tried, and what you recommend.
7. CI's `review` job has Claude review each push to the PR, post its findings as comments on the lines they concern, and update one summary comment that says which commit it reviewed, how many findings it posted, and anything it couldn't check. If the summary names something it couldn't check, tell the user. Answer every finding: either fix it and go back to step 2, or reply on the comment saying why not. The push with a fix is reviewed again.
   - A PR that changes `.github/workflows/ci.yml` isn't reviewed: the review runs only from the workflow as `main` has it, and passes without a summary otherwise. Keep a change to that file in its own small PR, so nothing else goes unreviewed with it.
   - If the `review` job fails without posting any comments, don't try to reproduce it locally or re-run it: it already tried twice, eight minutes each at most. Its log shows each attempt's turns and tool calls. Tell the user what it shows: an invalid or expired Claude credential secret, Claude unreachable, or where a review stalled. `check` can't pass until the job does.
8. Squash-merge the PR once all of these are true: `check` passed on the latest commit, the PR has no merge conflicts, every review finding is answered, and its base is `main`. If GitHub refuses the merge, go back to step 4.
   - Merge a red PR only once `check` passed with the `phone-ok` label on it, which is the owner's go-ahead to merge: until then, tell the user it's ready and wait. An OK in chat never stands in for the label. One red change goes live per deploy.
9. Don't deploy. Merging starts the Deploy workflow at once, and CI on `main`. When the PR's CI passed on exactly the code `main` now has (`worker/find-passed-ci.mjs`), which it did if the PR was up to date with `main` as it merged, that first Deploy run deploys, and CI on `main` skips the checks it already ran; otherwise the Deploy run that follows CI on `main` does. Either runs `worker/deploy.mjs`, which deploys each app's Worker and rolls back any new version that doesn't answer. An app's deploy is skipped when nothing but docs, tests, tooling, and other apps' folders changed since its live version's commit; `worker/deploy-scope.mjs` lists those files. Each line of the deploy log starts with its app's name, so read step 10's results for each app. When you add a file that can't change the Worker, add it to that list.
10. Wait for the Deploy runs for the merge commit to finish, then read their logs and do what matches:
    - The first says "No pull request's CI passed on exactly this code": the deploy waits for CI on `main`. Read the next Deploy run's log.
    - It says `worker check: ok`: the new version is live. Tell the user.
    - It says "Nothing the Worker runs changed": the merge didn't need a deploy, or the first Deploy run already deployed it. Tell the user which.
    - It says "has moved on": another merge landed first, and its Deploy run covers this one. Read that run's log instead.
    - The run was skipped: CI failed on `main`. Read the CI log, fix the failure in a new PR, and start again at step 1.
    - It says "nothing was deployed": the `production` environment has no Cloudflare token. Tell the user.
    - The run failed: read the log. If it says "the earlier version is live again", the Worker rolled back and is unchanged. Tell the user what failed and recommend a fix.
11. Run `npm run deploy:api` yourself only when step 10 found no successful deploy and the user agrees. Say why the automatic deploy didn't happen and recommend whether to deploy by hand. Never deploy any other way.
12. Related changes can ship together in one PR. Split work into several PRs only when its parts can be reviewed or rolled back on their own. A PR that needs another PR's unmerged changes doesn't wait for it: stack it. Start its branch from that PR's branch, open it into that branch, so its diff and review show only its own changes, and name the PR it builds on in its description. Whenever the earlier PR's branch changes, merge it into the stacked branch. Once the earlier PR merges, change the stacked PR's base to `main` if GitHub hasn't, merge `main` into its branch, and go back to step 2 for it. That merge conflicts wherever the stacked PR changed lines the earlier one did, since `main` has the earlier PR only as its squash: keep the stacked branch's side of those, and resolve any other conflict as step 4 says. Never merge a PR into another PR's branch: a stack merges into `main` one PR at a time, earliest first.

## Building and fixing

### Both apps, every place

- A fix or design change applies to both apps, and to every view, sheet, and theme where the same thing shows, unless the owner names one app.
- When only one app can have it now, build it in `shared/` so the other can add it later.
- When adding to one app something the other already has, reuse the other app's values, like logo sizes and spacing, and leave the other app untouched.
- A phone and a wide screen look the same, except where the width forces a difference.

### When something is wrong

- When fixing a bug, look for the same bug in all apps and in every view, sheet, and theme, and fix those in the same PR. Say what else you checked.
- When a bug reaches production or beta, the PR also says how it got there and why no test caught it, and adds the test or lint rule that would have. Prefer a test or lint rule over a written rule, which agents can forget.
- Say a bug is fixed only once you've reproduced it and seen the fix work.
- Ask for a Diagnostics report rather than guessing.
- While chasing a bug, test one idea at a time and say what each one showed. Never stack guesses in production.
- Once a bug is fixed, take out any attempted fixes that didn't help, and put back anything removed that turned out not to be the cause.
- When something replaces an old system, delete the old code in the same PR.

### What the apps should feel like

- Smooth above all. Nothing flickers, jumps, or flashes on open, return, reload, or redraw, and a new release arrives without anyone swiping the app closed.
- Follow general best practices for web development code and app UI.
- Desktop hover is a subtle change of text color only: never an underline, border, or highlight.
- Simple beats configurable. Pick good defaults rather than adding settings.
- Readable before elegant. Text that's too small, light, or dim is a bug: check it against the type scale, and against WCAG's AA contrast, 4.5 to 1, which the root's `tests/browser/contrast.mjs` checks wherever the browser tests check the type scale, and the WNBA's `tests/browser/themes.spec.mjs` in both its themes.
- Things shown side by side for comparison share one scale, like two pitchers' speed lines.
- Build with mature web features that work in every browser, Safari first.

## Writing

README and anything user-facing: be clear, direct, and concise.

On the pages, text of one sentence or less, like a label, an empty view's note, or a setting's note, ends without a period; text of two or more sentences, like a release note or a message that says what to do, ends with one. An outlet's own words keep their punctuation, in an element marked `data-quoted`. The root's `tests/browser/stray-periods.mjs` lists any shown text that breaks this, and each app's browser tests check every view with it, wherever they check the type scale.
